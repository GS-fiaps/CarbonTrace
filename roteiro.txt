 Roteiro de Apresentação — CarbonTrace (.NET)
Global Solution 2026/1 — FIAP

 PARTE 1 — A Ideia do Projeto

"O CarbonTrace nasceu de uma pergunta simples: como a tecnologia espacial pode ajudar a proteger as florestas brasileiras?"
O Brasil é dono de 60% da Floresta Amazônica, o maior bioma tropical do mundo. Mesmo assim, o desmatamento ilegal continua avançando — e o principal problema não é a falta de fiscalização, mas a falta de informação em tempo real. Quando um fiscal identifica uma área desmatada pela fiscalização tradicional, o dano já está consolidado.
Foi aí que enxergamos uma oportunidade. Satélites como o Landsat 8 da NASA, o Sentinel da ESA e o CBERS do INPE já circulam a Terra capturando imagens de alta resolução todos os dias. Esses dados existem, são públicos e estão disponíveis. O que faltava era uma plataforma que transformasse essas imagens em inteligência ambiental aplicada.
O CarbonTrace faz exatamente isso: consome imagens satelitais, detecta automaticamente variações na cobertura vegetal, gera alertas classificados por nível de criticidade e notifica os órgãos ambientais responsáveis como o IBAMA e as secretarias estaduais de meio ambiente.
O projeto se conecta diretamente ao tema da Global Solution — a economia espacial — e responde a três ODS da ONU: o ODS 13 sobre ação climática, o ODS 15 sobre vida terrestre e o ODS 11 sobre cidades sustentáveis.

 PARTE 2 — Questões Técnicas

Arquitetura e Boas Práticas

Como o projeto está organizado?

"O CarbonTrace foi desenvolvido seguindo os princípios do Clean Architecture, dividido em quatro projetos dentro da mesma solution."
O primeiro é o CarbonTrace.Domain, que é o coração da aplicação. Ele contém as entidades de domínio como Estado, Regiao, ImagemSatelital, Analise e Alerta, além dos enums e a BaseEntity. Esse projeto não depende de nenhum outro — ele é completamente isolado.

O segundo é o CarbonTrace.Application, que contém a lógica de negócio. Aqui ficam as interfaces dos repositórios, as interfaces dos services, as implementações dos services e os DTOs de request e response. Esse projeto depende apenas do Domain.

O terceiro é o CarbonTrace.Infrastructure, responsável pela persistência. Aqui ficam o DbContext, as Configurations do Entity Framework, as implementações dos repositórios e as Migrations. Esse projeto implementa os contratos definidos no Application.

O quarto é o CarbonTrace.API, a camada de entrada da aplicação. Aqui ficam os Controllers, as Extensions de injeção de dependência, o Swagger e o Program.cs. Esse projeto orquestra tudo.

Por que escolheram essa arquitetura?

"Escolhemos o Clean Architecture por três razões principais."

A primeira é a separação de responsabilidades. Cada camada tem uma função clara e bem definida. A lógica de negócio no Application não sabe nada sobre o banco de dados — ela só conhece interfaces. Se amanhã quisermos trocar o Oracle pelo PostgreSQL, só precisamos alterar a Infrastructure.

A segunda é a testabilidade. Como todas as dependências são injetadas por interfaces, é possível criar mocks para testar qualquer camada isoladamente.

A terceira é a manutenibilidade. Quando uma nova funcionalidade precisa ser adicionada, sabemos exatamente onde cada peça vai — entidade no Domain, interface e service no Application, controller na API.

Como vocês adicionariam uma nova funcionalidade?

"Vou dar um exemplo concreto: adicionar um módulo de notificação por e-mail quando um alerta crítico é gerado."

Primeiro, criaríamos a entidade Notificacao no Domain com seus atributos.

Segundo, no Application criaríamos a interface INotificacaoRepository e a interface INotificacaoService com os métodos necessários, além dos DTOs NotificacaoRequest e NotificacaoResponse.

Terceiro, no Application criaríamos a implementação NotificacaoService seguindo o mesmo padrão dos outros services.

Quarto, na Infrastructure criaríamos a NotificacaoConfiguration mapeando a entidade para o Oracle e a implementação NotificacaoRepository.

Quinto, na API criaríamos o NotificacaoController com os endpoints e registraríamos as novas dependências no CarbonTraceServiceCollectionExtensions.
Por fim, gerar uma nova Migration para adicionar a tabela no banco.


Banco de Dados e Relacionamentos
Como o banco foi modelado?

"O banco foi modelado seguindo a abordagem Code First do Entity Framework, com 11 tabelas normalizadas até a 3FN."
O modelo segue o fluxo natural do sistema: um Estado possui várias Regiões. Cada Região é fotografada por múltiplas Imagens Satelitais, capturadas por diferentes Satélites. Cada Imagem gera uma Análise de desmatamento. Quando a análise identifica uma situação crítica, um Alerta é emitido. Esse Alerta é então enviado para múltiplos Órgãos Ambientais através da tabela associativa AlertaOrgao.
Paralelamente, Usuários do tipo FISCAL podem registrar Ocorrências manualmente em campo, complementando os dados satelitais. Analistas geram Relatórios periódicos consolidando as informações.
Todo o mapeamento foi feito através de classes IEntityTypeConfiguration separadas por entidade, o que mantém o DbContext limpo e organizado.

Qual relacionamento foi implementado e por quê?

"Implementamos todos os tipos de relacionamentos."

O relacionamento 1:N é o mais presente — Estado para Regiao, Regiao para ImagemSatelital, ImagemSatelital para Analise, Analise para Alerta, Usuario para Ocorrencia e assim por diante.

O relacionamento N:N está presente entre Alerta e OrgaoAmbiental, através da tabela CT_ALERTA_ORGAO. Escolhemos esse relacionamento porque um alerta pode precisar notificar múltiplos órgãos — por exemplo, um alerta crítico na Amazônia pode acionar o IBAMA federal, a secretaria estadual e uma ONG local ao mesmo tempo.


O que acontece com os dados relacionados ao deletar um registro?

Todos os relacionamentos foram configurados com OnDelete(DeleteBehavior.Cascadde), ou seja,  exclusão em cascata.

"O sistema permite exclusão de registros que possuem dependentes."

Configuramos todos os relacionamentos com DeleteBehavior.Cascade. Isso significa que se você tentar deletar um Estado que possui Regiões cadastradas, o Oracle vai deleter.
Essa foi uma decisão consciente de design. Em um sistema de monitoramento ambiental, dados históricos são fundamentais. Não faz sentido deletar um Estado e perder todas as análises, alertas e ocorrências vinculadas a ele. A exclusão deve ser feita na ordem inversa das dependências, ou implementar um soft delete usando o campo Active que herdamos da BaseEntity.

Migration

O que são migrations e qual o papel delas no projeto?

"Migrations são o mecanismo do Entity Framework Core para versionar o schema do banco de dados junto com o código."
No CarbonTrace, quando definimos as entidades no Domain e suas configurações na Infrastructure, o EF Core consegue traduzir esse modelo em SQL para o Oracle. A Migration captura essa tradução em um arquivo versionado, que pode ser aplicado ou revertido de forma controlada.
No nosso caso, a Migration Initial criou todas as 11 tabelas com suas colunas, tipos de dados, chaves primárias, chaves estrangeiras e constraints — tudo isso sem precisar escrever uma linha de SQL manualmente.

Como vocês gerenciariam mudanças no banco ao longo do tempo?

"Cada mudança no modelo gera uma nova Migration incremental."
Por exemplo, se precisarmos adicionar uma coluna area_recuperada_km2 na tabela CT_ANALISE, o processo seria:
Primeiro, adicionamos a propriedade na entidade Analise no Domain.
Segundo, mapeamos a nova coluna na AnaliseConfiguration na Infrastructure.
Terceiro, geramos uma nova Migration com o comando:
dotnet ef migrations add AdicionarAreaRecuperada --project CarbonTrace.Infrastructure --startup-project CarbonTrace.API
Quarto, aplicamos no banco com:
dotnet ef database update --project CarbonTrace.Infrastructure --startup-project CarbonTrace.API
Cada Migration fica registrada na tabela __EFMigrationsHistory do Oracle, permitindo rastrear exatamente quais mudanças foram aplicadas e quando.

Demonstração
Como a aplicação trata entradas inválidas?

"O sistema tem duas camadas de validação."

A primeira camada é nos DTOs de request, usando Data Annotations do .NET. Por exemplo, no EstadoRequest, o campo Nome tem [Required] e [StringLength(100, MinimumLength = 2)]. Se o campo vier vazio ou com um caractere, o ASP.NET retorna automaticamente um 400 Bad Request com uma mensagem descritiva antes mesmo de chegar no Controller.

A segunda camada é no Controller, onde verificamos if (!ModelState.IsValid) return BadRequest(ModelState) antes de chamar o service.
Isso garante que apenas dados válidos chegam à camada de negócio e ao banco de dados.

Como vocês testaram as rotas da API?

"Utilizamos o Swagger UI como principal ferramenta de teste durante o desenvolvimento."
O Swagger foi configurado com o Swashbuckle e está acessível diretamente na raiz da aplicação em http://localhost:5222. Ele exibe todos os endpoints organizados na ordem correta de cadastro — começando pelo Estado e Satélite, que não têm dependências, até o AlertaOrgao, que depende de várias outras entidades já cadastradas.
Para cada endpoint testamos os cenários positivos com dados válidos, cenários negativos com dados inválidos para verificar as validações, e a ordem das dependências para garantir que as chaves estrangeiras estão corretas.

Documentação

Expliquem o diagrama do README com as próprias palavras.

"O diagrama do README mostra o fluxo de dados do sistema de fora para dentro."
Tudo começa no Estado, que é a base geográfica do sistema. Um Estado possui várias Regiões. Essas Regiões são monitoradas por Imagens Satelitais, que são capturadas por Satélites como o Landsat ou o Sentinel.
Cada Imagem Satelital gera uma Análise, que compara a cobertura vegetal atual com imagens anteriores e calcula o percentual de variação. Se essa variação ultrapassar determinado threshold, a Análise recebe um status crítico e gera um Alerta.
Esse Alerta é então conectado a múltiplos Órgãos Ambientais através da tabela associativa AlertaOrgao, que registra se a notificação está pendente, enviada, confirmada ou falhou.
Paralelamente, Usuários do tipo FISCAL podem registrar Ocorrências manuais em campo, e Analistas podem gerar Relatórios periódicos. Tudo isso está conectado ao mesmo modelo de dados.

Qual foi o maior desafio do projeto e como resolveram?

"O maior desafio foi a compatibilidade do Entity Framework Core com o Oracle."
O Oracle não suporta o tipo BOOLEAN nem o tipo GUID nativo do .NET da mesma forma que outros bancos. Quando geramos a primeira Migration, o EF tentou criar colunas BOOLEAN e RAW(16), que o Oracle rejeita com o erro ORA-00902: tipo de dados inválido.
A solução foi configurar explicitamente nas IEntityTypeConfiguration de cada entidade que os campos bool devem usar NUMBER(1) e os campos Guid devem usar VARCHAR2(36). Também adicionamos no ConfigureConventions do DbContext uma regra global para garantir essa conversão em todos os modelos.
Além disso, encontramos um problema com propriedades private set — o EF Core não conseguia instanciar as entidades corretamente sem que as propriedades fossem inicializadas no construtor primário. A solução foi garantir que cada propriedade fosse inicializada com o parâmetro correspondente, como public string Nome { get; set; } = nome.

O que mudariam se pudessem refazer?
"Três coisas principais."
A primeira seria implementar o soft delete desde o início, usando o campo Active da BaseEntity para desativar registros em vez de deletá-los. Isso preserva o histórico e evita problemas com as constraints de FK.
A segunda seria adicionar autenticação JWT desde o começo. O documento da GS de Java pede isso, e ter a autenticação no .NET também permitiria que o Mobile consumisse a API de forma segura com o mesmo token.
A terceira seria separar melhor os DTOs de criação e atualização. No projeto usamos o mesmo Request para o POST e o PUT, o que funciona, mas em alguns casos o update não deveria permitir alterar campos como IdEstado de uma Regiao, por exemplo. DTOs separados dariam mais controle sobre o que pode ser modificado.
